## 2. Findings

### F-B-1 (P1) — `ScanConfig` grew `ldm_resolver`; contract §5.1 shape is stale
- **Axis**: Data model / Wiring. **Verdict**: MISMATCH (contract drift).
- **Ours**: `include/cr/orchestrator/cr_scan.h:57-64` — `ScanConfig` now ends with `table::LdmDiskResolver ldm_resolver;` (added in `fffe597`, after the `183dfcd` pin; the only diff to the header since the pin, verified via `git diff 183dfcd..HEAD`).
- **Contract**: CORE-CONTRACT.md §5.1 lists `ScanConfig { run_quick; run_deep; run_carve; whole_disk; fs_hint; StageWeights; threads }` — no resolver field. §2.4's ownership table also lacks it (it is a `std::function` copyable member — ABI-relevant for an in-process MSVC shim).
- **Impact**: a UI shim compiled against the contract-described layout breaks; subprocess mode unaffected.
- **Fix**: add to §5.1 + §2.4 (borrowed-callable semantics: empty = single-disk; devices must outlive the scan), or re-pin the contract at HEAD.

### F-B-2 (P1) — LDM hook is now unconditional; §5.2 still claims `fs_hint==Unknown` gate
- **Axis**: State machine. **Verdict**: MISMATCH (contract drift; deliberate, rationale in code).
- **Ours**: `src/core/orchestrator/cr_scan.cpp:230-266` — `parse_ldm_database` is tried before the `fs_hint` switch on **every** engine pass; comment: probe_family's FAT heuristic (55AA + pow2 word @+0x0B) "can alias an LDM disk's boot-code bytes, which would gate this branch out (LDM audit finding)". At `183dfcd` the branch was `if (cfg_.fs_hint == FsFamily::Unknown)`.
- **Contract**: §5.2.3 "**LDM hook**: when `fs_hint==Unknown`, `parse_ldm_database` is tried".
- **Behavior change**: dynamic disks whose boot-sector bytes alias FAT are now detected. Cost on regular disks = one 512-byte read + self-rejection.
- **Fix**: update §5.2.3 (and note the probe ordering: LDM check precedes fs_hint dispatch).

### F-B-3 (P1) — Cross-disk LDM member registry added; §12 + G-19 ("single-disk scans only") stale
- **Axis**: Capability / Wiring. **Verdict**: MISMATCH (contract drift).
- **Ours**: `rrecov.cpp:447-479` — on whole-disk scans the CLI enumerates every disk (`enumerate_disks(32,…)`), opens each (RDA first), reads PRIVHEAD at LBA 6 (`memcmp "PRIVHEAD"`, GUID at +0x30), and installs `cfg.ldm_resolver` (shared GUID→device map, devices held open in `ldm_members`). `cr_scan.cpp:242-248` prefers it over the local single-disk resolver.
- **Contract**: §5.2.3 "single-disk resolver: members on other disks read as missing"; §12 "Multi-disk memberships beyond the scanned disk read as missing members — single-disk scans only (honest limitation)"; G-19 classified **by-design**.
- **Impact**: spanned/striped/mirrored/RAID-5 volumes across present disks now resolve in CLI scans — a capability the UI contract explicitly denies. UI capability claims must be updated.
- **Fix**: rewrite G-19 (now: resolves when member disks are openable; still one missing RAID-5 column max, Broken volumes still not scannable).

### F-B-4 (P1) — `fix --undo-apply` without `--disk` writes to **disk 0**
- **Axis**: Error surface / safety. **Verdict**: MISMATCH (our-code defect; no corpus needed).
- **Ours**: `rrecov.cpp:1049-1052` — the guard is `if (!have_disk && undo_apply_path.empty())`, so `rrecov fix --undo-apply log.undo` (no `--disk`) passes the guard; `disk` keeps its default `0` (line 1013) and `win::open_disk_rw(0, …)` (line 1077) opens **PhysicalDrive0 for write** and replays absolute-offset undo entries onto it.
- **Contract**: §13 grammar shows `fix --disk N … [--undo-apply file]` with `--disk` unbracketed (mandatory), but the parser does not enforce it in undo-apply mode.
- **Impact**: replaying a disk-1 undo log onto disk 0 corrupts disk 0 (undo entries are `(offset, length, original)` with absolute offsets).
- **Fix**: `if (!have_disk) { "fix needs --disk N"; return 1; }` — drop the `&& undo_apply_path.empty()`.

### F-B-5 (P2) — Progress granularity vs og: no live file count, no sector ticker, no remaining time
- **Axis**: Progress semantics. **Verdict**: MISSING (declared G-04/G-05; og-parity gap quantified here).
- **Ours**: progress callback carries only `overall_permille` (cr_scan.h:94-95); `bytes_scanned` is carve-only (cr_scan.cpp:563); `files_found` is visible only after `run()` returns; no sector position. The CLI shows `"\r  %5.1f%%  (%lld s)   "` (rrecov.cpp:83).
- **og**: runtime capture shows `"Advanced Scanning , Files Found: 1139157 (143.74 GB)"`, `"Remaining time: 07m43s | Reading sector: 134316032/31413598"`, and a live `"Searching: <path>"` ticker (dynamic-ground-truth--scan-phase-captured.md §7); remaining time implies a linear sector-throughput model; `CUIScanProgressInfo` "%1 file chunks scanned...", "%1 files %2 have been found." (04 §5.6).
- **Fix (capability honesty)**: surface a `(stage, files_found, bytes_done, bytes_total)` side-channel (extend ScanStats with atomics + a poll API, or widen the callback), or keep G-04/G-05 prominent in UI planning.

### F-B-6 (P2) — og's progress/cancel event model is 3-level with cancel gating; ours is a flat scalar
- **Axis**: Progress semantics / Capability. **Verdict**: DELTA (structural).
- **Ours**: one callback `bool(*)(u32 permille, void*)` + a separate `CancelToken*`; no stage ids, no counters, no cancel-gating.
- **og**: `CCallBackOperate` (CallbackOperator.mo, 29 exports; decompiled `re-workspace/reversed/ghidra-mo/CallbackOperator_decompiled.c`): ctor takes `ulong (*)(OC_PARAM*, void*)` + userdata (same fn-pointer+void* shape as ours); methods `StartOperation/StartChildOperation/StartFileSystemOperation/EndCurOperation/EndCurChildOperation/EndFileSystemOperation/SetCurChildOperationValue/IncrementCurChildOperation/SetLargeCounter/SetLargeCounterTotal/SetEnableUserCancel/DoMessageLoop/CallFunction` — a message-style callback with opcode word (verified opcodes: 2=EndCurOperation, 7=SetCurChildOperationValue, 8=IncrementCurChildOperation, 9=EndCurChildOperation, 0xC/0xD=SetEnableUserCancel(enable/disable), 0xE=DoMessageLoop, 0x10/0x11=SetLargeCounter(Total)); RAII progress objects; the same machinery streams repair progress (rawfixer-v2--method-inventory.md §2).
- **Meaning**: og reports *stage events* (start/end), *nested child progress*, *large counters* (files found / total), and *gates user cancel per operation*. Our weighted permille compresses all of that into one number; the UI cannot know which stage it is in except by inference.
- **Fix**: at minimum add a stage-id parameter (enum Quick/Deep/Carve/Recover) to the callback; consider a counter side-channel (see F-B-5).

### F-B-7 (P2) — og offers Pause during scan; we have none
- **Axis**: Capability. **Verdict**: DELIBERATE-DELTA (declared G-07).
- **Ours**: no pause/resume API (contract §5.4 "No pause. No resume."; `stage_done_mask` stored-never-consumed, cr_scan.cpp:573-574 vs 630-635).
- **og**: "Pause (❚❚) and Stop (■) controls in the bottom bar — the scan-control surface" (dynamic-ground-truth--scan-phase-captured.md §7 addendum, 7.6-min capture).
- **Fix**: keep the honest gap; if the UI promises parity marketing, pause must be re-scoped (a UI-side pause that simply delays enqueueing recoveries is possible without core changes; a scan pause is not).

### F-B-8 (P2) — Retry error map / cache counters not merged on the abort path
- **Axis**: Error surface / Behavior. **Verdict**: MISMATCH (code vs the natural reading of §5.2.1; contract ambiguous).
- **Ours**: `cr_scan.cpp:164-175` returns `stamp(rc)` immediately on stage failure; the merge `stats.errors.merge(retry->error_map())` + `cached_hits/misses` (lines 176-181) runs only on success. A scan that aborts mid-way reports an **empty** error map even when bad sectors were hit and zero-filled — and the CLI's `--log` then prints no `read-error range:` lines (rrecov.cpp:497-500) on exactly the runs where they matter.
- **Contract**: §5.2.1 "At the very end: `stats.errors.merge(retry pipe)`, cache counters copied, `tree_.refresh_stats()` (NOT called on the error path)" — the parenthetical attaches only to refresh_stats, implying merge-always.
- **Fix**: merge (and stamp counters) in `stamp()` or before each early return.

### F-B-9 (P3) — `lost::discover` failure is silently swallowed
- **Axis**: Error surface. **Verdict**: MISSING (diagnostic).
- **Ours**: `cr_scan.cpp:398-399` — `if (lrc == OK) { … }`: a failed discovery produces no error, no stat, no log line; deep still ticks 750 and the run succeeds with zero lost partitions. (Contrast: the remnant sweep's rc *does* propagate, lines 378-381/462.)
- **Fix**: surface as a stat or log (non-fatal is fine — matches "candidate misses never abort").

### F-B-10 (P3) — `PoolCancelToken` built but never wired in the candidate fan-out
- **Axis**: Threading / Wiring. **Verdict**: MISMATCH (dead code).
- **Ours**: `cr_scan.cpp:435` constructs `PoolCancelToken pool_cancel(&pool);` but the worker lambda (line 436-441) passes the **outer** `cancel` token to `scan_candidate`. The adapter is never used; an external `ThreadPool::abort()` would not be visible to in-flight candidate engines (they only see the caller's token).
- **Fix**: pass a token that ORs pool-abort with the caller token (or delete the dead object).

### F-B-11 (P3) — Parallel candidate path drops `deleted_found`
- **Axis**: Data model. **Verdict**: MISMATCH (internal inconsistency).
- **Ours**: sequential path adds `stats.deleted_found += deleted` (cr_scan.cpp:453); the parallel path collects `Out.deleted` ("unused for candidates", line 427) and never merges it (lines 442-445). Same scan, different `threads` ⇒ different `deleted_found`.
- **Fix**: merge `o.deleted` in the reduction loop (candidate engines do report it — cr_scan.cpp:482, 492, 500, 508…).

### F-B-12 (P3) — §13 progress-line spec omits the three trailing spaces
- **Axis**: Constants / output format (byte-level). **Verdict**: MISMATCH (doc).
- **Ours**: `rrecov.cpp:83` — `wprintf(L"\r  %5.1f%%  (%lld s)   ", …)` (3 trailing spaces, present identically at `183dfcd`).
- **Contract**: §13 "Progress line `\r  %5.1f%%  (%lld s)`". Also undocumented: the completion line `\r  100.0%%  done          \n` (rrecov.cpp:86).
- **Impact**: cosmetic for regex parsers; fatal for byte-exact diff tests.
- **Fix**: correct §13 (and document the done line).
