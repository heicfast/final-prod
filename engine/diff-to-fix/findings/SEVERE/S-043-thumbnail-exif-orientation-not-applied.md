# SEVERE S-043 — Thumbnails are not EXIF-oriented: the og rotates per tag 0x112 before the 256-px pass; the core does not

**Severity:** SEVERE
**Module:** preview (thumbnail engine)
**Parameters affected:** B2 (recovery/preview correctness — output bytes), A25 (algorithm steps), B1 (behavioral correctness of the new surface)
**Corpus references:** `DRWUI_decompiled.c` `FUN_1402fcc30` :521694-521725 (reads GDI+ property 0x112, applies RotateFlip 2→4/3→2/4→6/5→5/6→1/7→7/8→3); call order `FUN_1403d75b0` region :652307 (orientation) → :652309 (the 256-px thumbnail) — verbatim quotes in `evidence/decompiled-quotes/s8-thumbnail-pipeline.md` §1
**Core references:** audited `ff879f9` — `src/core/preview/cr_thumbnail.cpp` (grep: zero orientation/rotate/flip code; the EXIF walker :303-427 only feeds the embedded fast path), `include/cr/preview/cr_thumbnail.h` (no orientation in Thumbnail), `cr_preview.cpp:355` / `cr_preview.h:137` (orientation surfaced as a metadata string only); engine landed `05e6786` after the preview-module audit
**Status:** READ-ONLY FINDING — no fix applied

## Summary

Every thumbnail the og produces is EXIF-oriented: the still-image work
item reads the GDI+ property 0x112 (EXIF Orientation) and applies the
matching RotateFlip before calling the 256-px thumbnail scaler. The
core's new thumbnail engine applies no orientation — a portrait phone
JPEG (orientation 6) thumbnails sideways, an upside-down shot (3)
thumbnails upside-down.

## What the reference does

`FUN_1402fcc30` (:521694-521725): `GetPropertyItemSize(0x112)` →
`GetPropertyItem` → switch on the orientation byte → `RotateFlip` with
the standard mapping (2→4, 3→2, 4→6, 5→5, 6→1, 7→7, 8→3). In the
still-image work item the orientation call at :652307 immediately
precedes the thumbnail call at :652309 — orientation is part of the
thumbnail pipeline, not an optional display step (the UI-side HBITMAP
is produced already rotated).

## What our core does

`cr_thumbnail.cpp` has no orientation handling anywhere (verified by
grep and full read this session). `extract_metadata` reports
orientation as a string field (cr_preview.h:137), and the engine's
header documents no orientation semantics. The embedded-EXIF fast path
(:303-427) re-encodes whatever the embedded thumbnail contains — which
for camera JPEGs is usually already oriented, masking the gap for the
fast path but not for the full-decode path (small images decode
full-size, so a 2 MB portrait JPEG thumbnails unrotated).

## Gap

Falsifiable: plant a JPEG with EXIF orientation 6 (90° CW rotate
needed); og thumbnail = rotated; core thumbnail = unrotated. The
output RGBA bytes differ.

## Impact

User-observable wrong thumbnails on mainstream content — the majority
of modern phone photos carry orientation 6/8/3. The thumbnail engine
is the newest user-facing surface; shipping it without orientation
makes its output visibly wrong vs the reference on the most common
input class.

## Fix plan (for the engineering team)

1. Reuse the preview module's IFD0 walk (the EXIF reader in
   cr_preview.cpp already parses tag 274/Orientation for metadata) to
   fetch the orientation byte in `make_thumbnail`.
2. Apply the 8-case transform to the decoded RGBA (and to the
   embedded fast path's result when the embedded thumb is not already
   oriented — mirror GDI+ by applying to both paths).
3. Files: `src/core/preview/cr_thumbnail.cpp`, tests in
   `tests/unit/test_thumbnail.cpp`, a new fixture set (orientation
   1..8 variants of one image, generated by extending
   `scripts/gen_thumbnail_fixtures.py`).
4. Update cr_thumbnail.h's contract doc (orientation applied; output
   is display-oriented RGBA) + preview.md's thumbnail section.
5. Acceptance: orientation-6/8/3/2 fixtures produce rotated thumbnails
   byte-identical to a reference implementation's output; orientation
   1 unchanged; fuzz clean.
