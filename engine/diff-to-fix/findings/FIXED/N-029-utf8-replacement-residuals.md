# MINOR N-029 — UTF-8 replacement policy residuals from the S-005 fix (session-2 group)

**Severity:** MINOR (grouped) · **Modules:** session, engines (ext4/btrfs/zfs) · **Status:** READ-ONLY FINDINGS — no fix applied
**Parameters affected:** B10 (names), D12 (session persistence), D13-adjacent
**Audited commit:** `e93decf` · corpus `03ad46c`

The S-005 fix is og-parity in net effect (verified — see `resolved/findings/S-005-*.md`). Two residuals survive, both MINOR:

**N-016a — Replacement-count policy.** Core `cr_text.h:85-88`: one U+FFFD per bad lead byte + per-byte resync — `\xE6\x96x` → `FFFD FFFD x`. The og's restore path converts via `MultiByteToWideChar(CP_UTF8, dwFlags=0)` (`DRWUI_decompiled.c:264664-694`, invoked at `:357529`), which follows Windows' maximal-subpart policy → `FFFD x`. Same direction (substitute invalid bytes), different counts on multi-byte invalid runs. Restored filenames can differ in U+FFFD count. Fix: adopt maximal-subpart in `text::utf8_to_u16` (consume as much of the invalid sequence as forms a prefix of a valid one, then one FFFD — RFC 3629 §3.1's "maximal subpart" formulation). Tests: `Text.MaximalSubpartReplacement` vectors (`\xE6\x96x`, `\xF0\x80\x80\x80`, truncated-tail classes).

**N-016b — Substitution timing in saved sessions.** og `.rsf` keeps the **original** on-disk bytes in the name field (substitution happens at display/restore). Core `.crsf` stores the **substituted** name (decode happens at scan). A re-exported name or a session-diff against the og will differ for invalid-UTF-8 names even after N-016a. Fix: persist the raw bytes alongside the decoded name (a versioned `name_raw` field), and restore-file naming from raw when valid. Tests: `Session.RawNameRoundtrip`, `Writer.InvalidUtf8NameRestoredFromRaw`.

**Related:** resolved S-005 · OQ-S2M-2 (Btrfs og anchor for name conversion — NOT-FOUND in BtrfsSearchDLL)

**Open questions:** Whether DRWUI's display conversion uses the same dwFlags=0 path for the results grid as for restore (single site found at `:534592`; a second would strengthen N-016a).

## Resolution (N-016a portion — the maximal-subpart policy)

**Status:** FIXED (sub-item N-016a); N-016b (raw-bytes persistence in sessions) remains open — precise scope below
**Fixed in commit:** this session's text-policy batch (DFX12)
**Verified by:** `Text.MaximalSubpartReplacement` (the finding's named vectors: `\xE6\x96x` → ONE FFFD + 'x'; `\xF0\x80\x80\x80y` → ONE FFFD + 'y'; truncated-tail classes; continuation-only runs; mixed FFFD + valid CJK) + the four re-pinned policy tests (`Text.OverlongFormsRejectedAsReplacement`, `Text.SurrogateHalvesRejected`, `Text.BeyondUnicodeRejected`, `Text.TruncatedTailBecomesReplacement`). Fail-before executed on the stash-isolated pre-fix decoder: 4/5 RED (the old per-byte policy emitted "FFFD FFFFD x" for `\xE6\x96x`, 3-4 FFFDs for fully-read invalid sequences); all green post-fix. Full suite 594/594 linux-release.
**Resolution notes:** `text::utf8_to_u16` now follows RFC 3629 §3.1's maximal-subpart formulation — the same policy as MultiByteToWideChar(CP_UTF8, flags=0), the og's restore-path conversion (DRWUI :264664-694, invoked at :357529; the finding's OQ about a second display-path site stays open — the display grid's conversion site remains singly-cited). A truncated/interrupted sequence consumes its lead byte plus every continuation byte that extended it, emitting ONE U+FFFD; a fully-read but invalid sequence (overlong / surrogate half / beyond U+10FFFF) consumes all of it — one U+FFFD; C0/C1 are RFC-excluded at lead classification (no well-formed sequence begins with them), so their continuations surface as their own single-byte subparts (the C0 80 → two-FFFD expectation is pinned unchanged). Engine impact verified: the ext4/Btrfs/ZFS NonAscii tests and the Btrfs Latin-1 lossless test pass untouched (M-010's U+E000+byte mapping is a separate function); cr_ui's u8_to_u16 and the report escaper share the policy comment and inherit the behavior (names with torn tails now carry og-parity U+FFFD counts). N-016b REMAINS OPEN: the og's .rsf keeps the ORIGINAL on-disk bytes (substitution at display/restore), while the core's .crsf stores the decoded name — a versioned `name_raw` field + restore-from-raw is the fix; next concrete step: extend the crsf record schema (version bump, additive field) with `Session.RawNameRoundtrip` + `Writer.InvalidUtf8NameRestoredFromRaw` tests.
