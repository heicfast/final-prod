## Summary

The og's signature database is a data file: RAWSearchDLL opens `raw_signs.json` from the install tree at engine init (ifstream → size → read → tinyxml2 parse), so the base table is mutable without touching the binary — an operator or update can change header/tail signs in the field. The core compiles the generated table into the binary (`cr_rawsigns_data.cpp` via `scripts/gen_rawsigns.py`); the only runtime-mutable surface is the separate user-taught signature path (cr_usersigns, N-064/M-048 lineage). Behavior on the shipped corpus file is identical — the divergence is the packaging posture, and it is registered nowhere (neither PARITY-DELTAS nor any finding).

## What the reference does

At engine init, the og reads the install-tree `raw_signs.json` (deep-dive:54-59, quoted above): the 139-extension header/tail signature table is data, loadable/replaceable per install; the C++ analyser registry and the JSON table are complementary layers (census:121).

## What our implementation does

The core's equivalent table is `cr_rawsigns_data.cpp` — a generated source file compiled into the binary, regenerated by `scripts/gen_rawsigns.py`. There is no runtime file load of a base signature table; user-taught signatures live in the separate usersigns surface. No document registers the deliberate posture change (data file → generated code).

## Gap

Falsifiable claim: the og loads its base signature table from disk at engine init; the core's base table exists only as compiled-in generated data; no PARITY-DELTAS row or finding records the divergence as deliberate.

## Impact

- Low, and mostly prospective: field-updatable signatures (e.g. an out-of-band updated signs pack) are impossible without a rebuild in the core; an engineering pass or product decision could reasonably prefer either posture, but the audit trail must show the choice was made knowingly.
- No behavioral delta on the current corpus reference file (identical bytes either way).

## Reproduction / verification

Corpus doc evidence (strength-3): deep-dive:54-59 (the ifstream load, quoted); the install-tree file exists (`og-codebase/raw_signs.json`). Core evidence (strength-3): `cr_rawsigns_data.cpp` is a generated source (its header comment + `scripts/gen_rawsigns.py`); `rg "ifstream.*raw_signs|raw_signs.json" src/` → no runtime load.

## Fix plan (for the engineering team)

1. Decide the posture and register it: either (a) keep compiled-in and add a PARITY-DELTAS row ("base signature table compiled in — reproducibility over field mutability; user-taught signatures cover the runtime-extension surface"), or (b) move to a shipped data file loaded at init with a SHA-pinned fallback to the compiled table (matching the og's mutability).
2. If (b): ship the generated table as a data artifact in the release zip (the PREBUILT-ARTIFACTS conventions already exist), load at engine init, and keep the compiled copy as the integrity fallback.
3. Acceptance criteria: the chosen posture is registered; if (b), a test that a data-file override is honored and that a corrupted file falls back to the compiled table.
