## The privilege decision tree

- **Install**: UAC #1 via `RequestExecutionLevel admin` (nsi:151). The inner setup + ProgramData creation run inside this one elevation; no second prompt (engine kit copy needs no extra rights). Declined UAC ⇒ installer never runs.
- **App launch (shortcut / Explorer / Start Menu)**: the exe has **asInvoker** semantics (see manifest truth) ⇒ **NO UAC at launch** — the user's report is exactly what the code produces. One exception: the installer **Finish-page "Launch" checkbox** executes the exe as a child of the still-elevated installer (`MUI_FINISHPAGE_RUN`, nsi:164 — MUI's `Exec` inherits the admin token), so the very first run can be elevated by inheritance, not by manifest; every later shortcut launch is unelevated.
- **Unelevated run**: frontend `ElevationBanner` (below) shows immediately — `useSecurityPosture()` (`ui/src/queries/system.ts:42-51`) → `system_security_posture` (`ui/src-tauri/src/commands/system.rs:70-79`) → own TokenElevation probe (`system.rs:37-60`, mirrors `engine/src/win/cr_elevate.cpp:12-21` / `include/cr/win/cr_elevate.h:19-23`: false for standard users AND non-elevated admins). Engine side, every raw-disk verb refuses `ERR_ELEVATION_REQUIRED 0x500C0001` (`engine/include/cr/cr_error.h:120`): `open_disk_impl` (`engine/src/ui/cr_ui.cpp:1433-1438`), `open_volume_impl` (:1488-1493), `open_volume_with_key` (:1575-1580), `image_create_impl` (:1725-1730); CLI refuses with 3-line stderr + exit 4 (`engine/src/app/rrecov.cpp:526-537`). In the UI, scan start maps the code to `BridgeError::engine(0x500c0001)` (`ui/src-tauri/src/commands/scan.rs:198-205`; lost-partition the same, `commands/lost_partition.rs:155`) → connector `'elevation-required'` (`ui/src/connector/tauri/tauri-connector.ts:131`) → reasonKey `errors.elevationRequired` = "Administrator privileges are required… Restart the app as administrator." (`ui/src/i18n/en.ts:536-537`), toasted at `ui/src/features/device-selection/home-page.tsx:97-98`.
- **Prompt / relaunch**: banner button → `system_relaunch_elevated` (`system.rs:84-124`): `ShellExecuteW(NULL, "runas", <own exe>, …, SW_SHOWNORMAL)` (:93-103) → **the OS UAC consent dialog is the only elevation surface**; on success the unelevated instance `app.exit(0)` (:113). Banner body: `elevation.bannerBody` = "Direct disk access requires administrator privileges — scanning and recovery are disabled until the app runs elevated." (`en.ts:486-488`).
- **UAC declined / runas fails**: `ShellExecuteW` returns ≤32 → `BridgeError::bridge(code::DEVICE_PERMISSION, "the elevation request was refused …")` (`system.rs:105-111`) → toast.error in the banner (`elevation-banner.tsx:36-40`); the old instance stays alive. No retry loop, no service fallback — by design ("never a degraded mode", `README.md:17-19`).
- **Engine `is_elevated` gates** beyond the ABI opens: `fsck_volume` returns ERR_UNSUPPORTED unelevated (`engine/src/win/cr_fsck.cpp:85-86`); health opens `\\.\PhysicalDriveN` GENERIC_READ|WRITE and reports "administrator rights required" text on open failure (`cr_ui.cpp:4887-4894`); BitLocker auto-unlock denial carries `ERR_FVE_ELEVATION_REQUIRED 0x50060002` (`cr_ui.cpp:1466-1475`).

## The manifest truth (verified)

**There is NO application manifest anywhere in the product's own tree.** Verified: no `.manifest`/`.rc` file under `ui/` (glob `**/*.{manifest,rc,rc2}` = 0 hits); `ui/src-tauri/build.rs` contains only link-search wiring + `tauri_build::build()` (:21-39); `Cargo.toml` has `tauri-build = { version = "2", features = [] }` (`ui/src-tauri/Cargo.toml:12`) — no custom manifest attr; `tauri.conf.json` carries no manifest/executionLevel key (full file read, 54 lines). **Mechanism today**: the exe's embedded manifest is produced by `tauri_build::build()` itself — Tauri 2's build crate emits its stock Windows manifest (`requestedExecutionLevel Level="asInvoker"`) into the resource section at compile time via its resource-embedding path; `tauri.conf.json` v2 exposes no knob for execution level, so nothing in this repo can change it. Result: `recovery-wizard-ui.exe` = GUI subsystem (`#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`, `ui/src-tauri/src/main.rs:2`) + asInvoker ⇒ launches unelevated, exactly as the user reported. Therefore every claim of "the app itself runs elevated (requireAdministrator)" is **documentation hallucination**: `installer/recoverywizard.nsi:27-29`, `installer/README.md:55-56, 83`, `docs/INTEGRATION-PLAN.md:24, 936-945`, `docs/INSTALL-FOOTPRINT-CURRENT.md:205` (contradicted by its own :377-378), `worklog/INTEGRATION-PLAN.md:858`. The repo's own spot check already recorded this (`worklog.md:2173-2182`), and the T15 probe `tools/forensic/collect-facts.ps1:32` greps the installed exe bytes for `requireAdministrator` — it would report `as-invoker-or-highestAvailable`. Fix path (not applied, read-only): ship an app manifest with requireAdministrator (reference parity, `worklog/context-sheets/REFERENCE-INSTALLER.md:617-618`) or keep asInvoker + the existing runas flow — but then the docs must stop claiming parity.

## The restart prompt styling audit

Component: `ui/src/features/consent/elevation-banner.tsx` (mounted once in the shell above `<Outlet/>`, `ui/src/app/shell.tsx:350` — persists across all routes). Renders only when posture resolves `administrator:false` (:21-22).

Exact styling (:25-45): container `role="alert"` with **hardcoded Tailwind amber palette** — `border-b border-amber-300 bg-amber-50 px-4 py-2 text-[13px] text-amber-900 dark:border-amber-500/40 dark:bg-amber-500/10 dark:text-amber-200`; `ShieldAlertIcon size-4`; button = `Button variant="secondary" size="sm"` overridden with `h-7 border-amber-400 bg-transparent text-amber-900 hover:bg-amber-100 dark:text-amber-200 dark:hover:bg-amber-500/20`; decline/UAC-fail surfaces as a sonner `toast.error` (:36-40).

Why it reads off-theme (the user's "weird popup colour and background"):
1. **It bypasses the app's entire token system.** The app has a two-layer design-token architecture — adopted raw tokens (`ui/src/theme/adopted/tokens.css`) → semantic mapping (`ui/src/styles/tokens.css`) → Tailwind `@theme inline` (`ui/src/styles/index.css:17-52`) — with dedicated warning tokens: `--warning #a84c07`, `--warning-vivid`, `--warning-muted` (16% amber wash; `styles/tokens.css:71-73`), plus dark-family (:157) and high-contrast overrides (:212-214, :263-265). The banner uses none of them; Tailwind's stock `amber-50/300/400/900` are external hex values that match no token.
2. **Theme-blind beyond one dark variant.** The app ships 5 themes (light, dark, ember, tide, blossom — `theme/adopted/tokens.css:25-427`) + a `.hc` high-contrast mode (`styles/tokens.css:185-278`). The banner only handles `dark:` generically; on ember (espresso/gold surfaces, :296-335) or tide (marine, :343-377) the amber wash clashes; in `.hc` it is completely unadapted (flat-surface/no-wash rules violated).
3. **Chromatic clash with the shell.** The light shell is a blue-tinted frame `bg-[#EBF2FF]` with white rounded main card (`app/shell.tsx:130, 341`) — a saturated amber band with a hard `border-b` (no radius, no elevation) sits like a foreign OS-styled strip pasted inside the card.
4. Same hardcoded-amber pattern also in the ConsentModal icon (`consent-modal.tsx:85`, `text-amber-500`), so the family is consistent only with itself.
