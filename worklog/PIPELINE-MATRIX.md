## Verdict — where the pipeline actually loses results

1. **Streaming (THE gap)**: the product detects and stores results correctly during scan (FS engines
   and carve populate ResultTree live), but **no result row ever crosses the engine→UI event surface
   until the UI pulls a snapshot** (10%-bucket invalidation). The og pushes rows live through its
   message bus. Fix = per-result event + bridge forward + UI incremental append (Phase 3).
2. **Detection strength**: coverage is at/near parity; the weak spots are grading coverage (S-058
   inverted gate, deep-read only index==0) and the 8 MiB tail-walk bound vs og's 200 MiB (Phase 2
   targets).
3. **DB/cache**: the og's persistence model is the .rsf session store (no SQL database); the product's
   CRSF already matches that role and adds mid-scan checkpointing. Phase 4 = polish, not rewrite.
