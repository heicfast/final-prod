## Bring-up findings (the audit trail — every one fixed with a cited run)

E2E-1 the ReFS product-surface finding above; E2E-2 GetBootClusterSize read
the exFAT shift bytes at +0x78/+0x79 (boot_code) instead of +0x6C/+0x6D
(cr_exfat_wire.h) — bpc ~2^50, Int64 overflow in every extent computation;
E2E-3 shard scenario order followed the matrix array, not the shard's
declared order; E2E-4 NtfsData parsed GET_NTFS_VOLUME_DATA at wrong offsets
(mft_corrupt had never completed in any recorded lane) → the NTFS boot-BPB
parse; E2E-5 the release kit staging missed the shipped libz/lz4/zstd
runtime DLLs; E2E-6..8 the PARTDEL-after-PARTOVR storage states (access-path
detach at the right layer, the partition-aware reseed, the FS-touch
auto-remount; the exFAT-specific limbo is handled by the exfat-b PARTDEL-first
order with the PROVEN recreation reseed); E2E-9 CorruptMft settle+retry for
the runner scanner's lingering handles; E2E-10 NtfsData read-only (no
self-inflicted dismount); E2E-11 clusters_per_record is i8 at +0x40, not
Int64; E2E-12 the completeness gate is profile-scoped (the assemble of this
very run false-failed on the smoke lane's rows before the fix). The CI
artifacts for every intermediate run carry the evidence; worklog.md is the
chronological record.
